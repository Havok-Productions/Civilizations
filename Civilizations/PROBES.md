# Commanded task probes

Run `/civ debug probe`. It finds the nearest loaded controlled villager in your current world, reports its UUID and distance, and selects its current task or nearest available queued task for a 120-second observation window. Selection queries each worker on its own Folia scheduler, including workers across region boundaries, with no 16-block/8-block search box. Workers that unload or fail to respond within four seconds are reported as unavailable. No chunks are loaded for this command. Work uses actual inventory, community supplies, gathering, crafting, smelting, navigation and construction.

- `/civ debug probe status` shows the nearest worker's latest result.
- `/civ debug probe jobs` lists its nearby unfinished tasks and IDs.
- `/civ debug probe start nearest <job-id> 180` attempts that specific queued task for a three-minute window.
- `/civ debug probe cancel` ends the diagnostic assignment. Normal village work continues.
- `/civ debug probe proposals` lists the nearest worker's retained construction proposals and rejection reasons.
- `/civ debug probe trial` explicitly admits the nearest worker's retained proposal as an experimental construction project and probes its first available action.
- `/civ debug probe trial nearest <proposal-id> 180` tries a specific proposal and observes its assigned action for three minutes.

Console commands replace `nearest` with a worker UUID from `/civ debug details`. For example: `civ debug probe start <worker-uuid> <job-id> 120`. All entity/world access is scheduled on that villager's owning Folia region. The existing `civilizations.admin` permission applies.

The chosen task remains the probe's goal while ordinary prerequisite gathering and recovery run. Existing interrupted work is checkpointed. Task claims, predecessor order, retry cooldowns, bedtime, village pause and physical/protection checks still apply and appear in the report. `start` probes existing work; `trial` explicitly admits a retained proposal despite village-need, active-project-slot, wall-purpose or predicted whole-site route rejection. The original rejection and bypassed predictions are saved. Runtime navigation and recovery get the opportunity to try the approach.

Trials still need a parseable geometry and observed blocks from which executable actions can be generated. They do not invent support, resources or observations, or silently move a mislocated layout. The survey covers the actual footprint; an unloaded site reports its world coordinates. An unexecutable trial retains its proposal and records `design_trial_admission` with `admitted=false`, without claiming that a villager attempted construction. A successfully admitted project remains normal village work after probe timeout or cancellation. Cancelling a pending survey prevents admission if the cancellation reaches it first; already admitted jobs remain queued. A first-action `PASS` is **not** proof that the entire wall or house is complete.

Results are written to `plugins/Civilizations/debug/probes/events.jsonl`, independently of general debug logging, with five-second observations, failure evidence and a final outcome. Final results also appear in the server log. Evidence includes task/target, elapsed time, position, maximum observed displacement from the starting position, inventory delta, observed target block, navigation evidence and the last failure. Displacement can include vanilla wandering; it is not proof of successful task navigation.

Alpha.35 also records command refusals: `probe_not_started` identifies selection/region failures and `probe_command` saves worker replies even when no execution begins. Task availability now names the actual claim, cooldown, preparation phase, support or reservation dependency. Automatic selection falls back to another available job if the previous task is unavailable. A command refusal is not a failed physical trial or proof that the architect rejected every plan.

Alpha.36 adds `probe_selected` with sampled worker position and distance, and `design_trial_requested`, `design_trial_admission`, `design_trial_probe` and `design_trial_result` to link the rejected blueprint to its actual assigned-action receipt. These are admin-commanded experiments, not automatic model self-training. The grass classification adapter now keeps observed passability independent of removability, so learning `SHORT_GRASS -> CLEARABLE` cannot itself block a route's starting cell.

Alpha.37 applies local coordinate recovery to new proposals, automatic retries, model revisions and explicit trials. If a layout is detached from every known village neighborhood, the host first checks the two common world/relative-coordinate mistakes, then translates the same shape toward the inhabited area if needed. A misplaced wall is centered on a nearby village landmark when its repaired contour still encloses none. This preserves the proposal identity, original blueprint, dimensions, goal and revision history. It does not impose a maximum construction distance: layouts connected to a known neighborhood can extend beyond the current local survey. The revised footprint must still pass fresh terrain validation. `designs/<village>-coordinate-recovery.json` records the move, and `<village>-rejection.json` records the precise failure, actual world footprint, distance to village anchors, observation coverage and next recovery action. Rejection records explicitly distinguish planning checks from started execution.

`PASS` requires the selected task's actual executor to commit a verified world change. Movement, a model response, inventory changes, a supply subtask or another worker completing the task cannot independently pass the probe. `ALREADY_SATISFIED` means no new action was demonstrated. `TIMEOUT` means the observation window ended without verified completion, not that the task is impossible. `CANCELLED` and `INTERRUPTED` retain their reasons. Probe expiry releases the diagnostic preference; it does not delete jobs, undo work, restore items or stop ordinary village activity. Results are diagnostic execution evidence, not a benchmark of autonomous model planning.
